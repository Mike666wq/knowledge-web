- 目前我们主流的硬盘主要有两种形态，一种是及机械硬盘(HDD)，一种是的固态硬盘(SSD)

# 1. 硬盘工作原理💽

## 1.1 机械硬盘 (HDD)

机械硬盘 (Hard Disk Drive, HDD) 通过机械部件读写数据。其内部由高速旋转的磁性盘片、可在盘片上移动的磁头及机械臂构成。数据以磁性方式存储在盘片的同心圆上。

由于读写过程涉及盘片旋转和机械臂寻道，HDD存在固有的机械延迟，因此随机读写性能相对较弱。同时，长期运行带来的机械磨损会导致磁头定位精度下降，可能引发速度变慢、文件损坏等问题，这也是老旧电脑运行卡顿的常见原因之一。

![image-20260325161344910](21.存储管理/image-20260325161344910.png)

## 1.2 固态硬盘 (SSD)

固态硬盘 (Solid State Drive, SSD) 基于闪存 (Flash) 技术，数据通过主控芯片写入浮栅晶体管来存储和读取。

![image-20260325161702257](21.存储管理/image-20260325161702257.png)

由于没有机械运动部件，SSD的读写完全依赖数字电路，因此访问延迟极低，随机读写性能远超HDD。但其也存在局限性：

- **写入寿命**：闪存单元有写入次数上限（P/E次数），达到一定次数后性能会下降甚至失效。
- **数据恢复**：一旦损坏，数据恢复的难度和成本通常高于HDD。

因此，尽管SSD在个人电脑中日益普及，但在对成本和数据可靠性要求极高的企业级存储场景，HDD依然是主力。

# 2. 硬盘设备命名🏷️

在Linux系统中，不同类型的磁盘设备有不同的命名规则：

- **物理磁盘**：使用 `sd`前缀加小写字母标识，如系统中的第一块硬盘为 `/dev/sda`，第二块为 `/dev/sdb`，以此类推。
- **磁盘分区**：在物理磁盘名后加上数字表示，如 `/dev/sda1`、`/dev/sda2`等。
- **其他设备**：
  - **NVMe 固态硬盘**：通常命名为 `/dev/nvme0n1`、`/dev/nvme0n2`。
  - **U盘/移动硬盘**：通常也使用 `sd`前缀，如 `/dev/sdc`。

# 3. 分区表🗺️

分区表是硬盘上的一块特殊区域，用于记录分区信息，帮助操作系统识别和管理磁盘布局。主流的分区表格式有MBR和GPT两种。

| 特性         | MBR (主引导记录)                                             | GPT (GUID 分区表)                                            |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **管理容量** | 最大支持约 **2 TiB**。                                       | 理论支持高达 **18 EB**，足以应对当前及未来的大容量硬盘。     |
| **分区数量** | 最多 **4 个主分区**。若要创建更多分区，需使用**扩展分区**，其内部可划分多个逻辑分区，但在分区表中仅算作1个。 | 支持数量极多（Windows系统通常限制为128个），管理更灵活。     |
| **系统引导** | 需要一个标记为“**活动 (Active)**”的主分区，用于存放引导文件 (Boot Loader)。 | 需要一个 **EFI 系统分区 (ESP)** 来存放UEFI引导文件。通常还包含一个MSR (微软保留分区)。 |
| **兼容性**   | 兼容所有操作系统，是传统的标准格式。                         | 需要系统支持UEFI启动模式。                                   |

- 启动流程简述
  - **MBR 磁盘**：BIOS/UEFI 读取 MBR，找到“活动分区”，然后加载并执行其中的引导程序。

![image-20260325162755086](21.存储管理/image-20260325162755086.png)

- **GPT 磁盘**：固件读取 EFI 分区中的引导程序，再加载操作系统。缺少 EFI 分区通常会导致无法从GPT磁盘启动。

![image-20260325162806491](21.存储管理/image-20260325162806491.png)

![image-20260325164116167](21.存储管理/image-20260325164116167.png)

电脑启动的时候：

- MBR分区表会找到激活分区，从里面加载系统启动；

- GPT分区表会查找EFI分区，没有是开不了机的，所以GPT分区表情况下需要建立ESP，MSR分区。

- MSR是微软保留的引导分区，分区一般不会坏因此一般不需要。

- ESP建立512MB，对齐到扇区整数倍是指一次读写几个扇区（例如新建个txt只写一个字符，依旧占用4K，除非越写越大超过4K，占4K的整数倍），并不是越大越好也不是越小越好，根据实际需求，一般是4KB。

# 5. 存储结构与磁盘划分📂

Linux系统采用单一的树形目录结构，所有文件和目录都从根目录（`/`）开始。理解各目录的用途是系统管理的基础。

#### 常见目录功能解析

| 目录名称         | 功能说明                                                     |
| ---------------- | ------------------------------------------------------------ |
| `/`              | **根目录**：整个文件系统的起点，所有其他目录和文件都挂载于此。 |
| `/boot`          | **启动目录**：存放系统启动所必需的文件，如内核 (`vmlinuz`)、初始内存盘 (`initrd`) 和引导加载程序 (`GRUB`) 配置。 |
| `/dev`           | **设备文件目录**：将硬件设备抽象为文件，如硬盘 (`/dev/sda`)、终端 (`/dev/tty`)。 |
| `/etc`           | **配置文件目录**：存放系统和绝大多数应用程序的配置文件，如用户账户 (`/etc/passwd`)、网络 (`/etc/hosts`)。 |
| `/home`          | **普通用户家目录**：每个用户在此拥有以自己用户名命名的子目录，用于存放个人数据和配置。 |
| `/root`          | **root用户家目录**：系统管理员（root）的主目录，区别于普通用户的 `/home`。 |
| `/bin`           | **基础命令目录**：存放系统启动和单用户模式下必需的基本命令，如 `ls`, `cp`, `bash`。 |
| `/sbin`          | **系统管理命令目录**：存放系统管理和维护相关的命令，如 `fdisk`, `ifconfig`，通常仅root可用。 |
| `/lib`/ `/lib64` | **共享库目录**：存放 `/bin`和 `/sbin`中程序依赖的共享库文件。`/lib64`专为64位系统提供。 |
| `/media`         | **可移动媒体挂载点**：系统自动挂载U盘、光盘等可移动设备时使用的目录。 |
| `/mnt`           | **临时挂载点**：管理员手动挂载文件系统（如新硬盘分区）时常用的目录。 |
| `/opt`           | **第三方软件目录**：用于安装非系统自带的商业或大型第三方软件。 |
| `/srv`           | **服务数据目录**：存放由系统提供的服务（如HTTP、FTP）所使用的数据文件。 |
| `/tmp`           | **临时文件目录**：所有用户均可读写，系统重启后内容通常会被清空。 |
| `/proc`          | **内核与进程信息虚拟文件系统**：不占用磁盘空间，实时反映内核、进程及系统状态，如 `/proc/cpuinfo`。 |
| `/sys`           | **设备与驱动信息虚拟文件系统**：与 `/proc`类似，提供设备、驱动和内核参数的接口。 |
| `/usr`           | **用户程序目录**：存放系统级的只读数据，如应用程序、库文件和文档。其子目录包括： • `/usr/bin`, `/usr/sbin`: 大部分用户和管理命令。 • `/usr/local`: 用户自行编译安装的软件。 • `/usr/share`: 共享数据，如帮助文档。 |
| `/var`           | **可变数据目录**：存放日志、缓存、邮件队列等频繁变化的文件，如 `/var/log`。 |
| `/lost+found`    | **文件系统恢复目录**：当文件系统发生错误时，`fsck`工具会将恢复的文件片段存放在此。 |

# 6. 物理设备的命名规则⚙️

在Linux中，硬件设备被抽象为设备文件，存放在 `/dev`目录下。了解其命名规则有助于管理磁盘和分区。

#### 常见设备文件

| 硬件设备      | 设备文件示例                      | 说明                               |
| ------------- | --------------------------------- | ---------------------------------- |
| IDE 硬盘      | `/dev/hda`, `/dev/hdb`            | 较老的设备接口，新系统已基本淘汰。 |
| SCSI/SATA/U盘 | `/dev/sda`, `/dev/sdb`            | 目前最常见的硬盘和U盘命名方式。    |
| 软驱          | `/dev/fd0`, `/dev/fd1`            | 基本已淘汰。                       |
| 打印机        | `/dev/lp0`- `/dev/lp15`           | 并行端口打印机。                   |
| 光驱          | `/dev/cdrom`, `/dev/sr0`          | 后者是更通用的SCSI光驱设备名。     |
| 鼠标          | `/dev/mouse`, `/dev/input/mouse*` | 具体名称取决于驱动和接口。         |
| 磁带机        | `/dev/st0`, `/dev/ht0`            | SCSI磁带机和IDE磁带机。            |

#### 硬盘与分区命名详解

当前主流的硬盘设备名均以 `/dev/sd`开头。命名规则如下：

- **硬盘标识**: `sd`后面的小写字母 (`a`-`p`) 代表第几块硬盘。例如：
  - `/dev/sda`：第一块硬盘
  - `/dev/sdb`：第二块硬盘
- **分区标识**: 在硬盘名后加数字表示分区。编号规则与分区表类型相关：
  - **主分区和扩展分区**：编号从 `1`到 `4`。
  - **逻辑分区**：编号从 `5`开始，即使前面只有1个主分区，逻辑分区也从 `5`开始编号（如 `sda5`, `sda6`）。

**示例解析：**

- `/dev/sda1`：第一块硬盘 (`sda`) 的第一个分区，通常是主分区。

- `/dev/sda5`：第一块硬盘的第一个逻辑分区，意味着该硬盘至少有1个扩展分区。

# 7. 文件系统与数据资料📂

分区完成后，需要为其建立一套“管理规则”，即**文件系统 (File System)**。它规定了数据如何存放、如何索引、如何保证一致性，从而让用户能像操作普通文件一样使用磁盘空间。

Linux支持多种文件系统，从宏观上可分为两类：

- **日志式文件系统 (Journaling FS)**：如 Ext3/4, XFS。通过记录日志来保障数据一致性，适合对可靠性要求高的场景。
- **索引式文件系统 (Indexed FS)**：如 Ext4, XFS。通过 inode 索引表管理数据块，是 Linux 的主流选择。

[![日志文件系统1](21.存储管理/日志文件系统1.jpeg)](https://git.inmind-lab.com/aaronxu/Linux-book/src/branch/main/01.Linux基础/09.存储管理/日志文件系统1.png) [![日志文件系统2](21.存储管理/日志文件系统2.jpeg)](https://git.inmind-lab.com/aaronxu/Linux-book/src/branch/main/01.Linux基础/09.存储管理/日志文件系统2.png)

## 7.1 Linux常见的文件系统🗂️

| 文件系统 | 类型   | 主要特点                                                     | 适用场景                                          |
| -------- | ------ | ------------------------------------------------------------ | ------------------------------------------------- |
| **Ext3** | 日志式 | • 在 Ext2 基础上增加日志功能，支持从 Ext2 原地升级。 • 提供 `data=journal | ordered                                           |
| **Ext4** | 日志式 | • Ext3 的改进版，RHEL 6 及许多发行版的默认文件系统。 • **大容量**：支持 1EiB 卷和 16TiB 单文件。 • **高性能**：引入 extents、多块分配、延迟分配等机制，减少碎片，提升大文件性能。 • **高可靠**：支持日志校验和、在线碎片整理、无限子目录等。 | 通用场景，适合个人电脑、服务器及虚拟机。          |
| **XFS**  | 日志式 | • 高性能日志文件系统，RHEL 7 及以后版本的默认选择。 • **高吞吐**：专为高并发、大文件、顺序 I/O 优化，延迟低。 • **快速恢复**：日志机制对性能影响小，宕机后恢复速度快。 • **超大容量**：支持高达 18EB 的存储。 | 数据库、文件服务器、大数据处理等 I/O 密集型场景。 |

------

### ⚙️ 格式化：构建文件系统的内部布局

执行 `mkfs`命令格式化分区时，内核会为其创建一套完整的内部结构，主要包括：

1. **初始化核心元数据**
   - **超级块 (Superblock)**：记录文件系统全局信息，如块大小、总块数、inode 总数、状态等。它是文件系统的“总地图”。
   - **块组描述符表**：当分区较大时，文件系统会被划分为多个块组 (Block Group)，此表记录各块组的管理信息，便于崩溃后局部恢复。
2. **构建 inode 与数据区**
   - **inode 表 (inode table)**：存放所有文件的元数据（属性），每个文件对应一个 inode。
   - **数据块区 (data blocks)**：实际存储文件内容的地方。
3. **建立日志区 (Journal)**
   - 日志式文件系统会划出专门的日志区域，用于记录待提交的操作，以保证数据一致性。

> **纠正说明**：
>
> 您提到的“日志式先干掉inode表，索引式先干掉第一个索引”的说法不准确。
>
> 正确的理解是：格式化会**初始化**整个 inode 表和数据区。而“索引”的概念体现在 inode 内部，它通过指针指向数据块，而非“删除第一个索引表示空间可用”。

------

### 📄 inode：文件的“身份证”与“数据指针”

每个文件都唯一对应一个 inode，它不存储文件名，而是记录了文件的详细属性和数据位置。关键字段包括：

- **文件元信息**：权限 (rwx)、所有者 (owner/group)、大小 (size)、时间戳 (atime/mtime/ctime)、特殊权限 (SUID/SGID/SBIT) 等。
- **数据块指针**：指向文件数据所在的磁盘块。对于大文件，会使用多级间接指针或 extents (区段) 来管理。

**inode 数量与耗尽问题**

- inode 总数在格式化时确定，通常远大于文件数量。
- 可能出现磁盘空间未满，但 inode 已耗尽的情况。这通常是由于存在海量小文件导致。
- 使用 `df -i`命令可以查看 inode 的使用情况。

------

### 🔗 目录、文件名与数据的关系

目录本质上是一种特殊的文件，其内容是一张“目录项 (dentry)”列表，记录了“文件名 → inode 编号”的映射关系。通过文件名找到 inode，再通过 inode 找到数据块，这就构成了 Linux 中“一切皆文件”的基础。

------

### 🌉 VFS：统一的虚拟文件系统接口

为兼容 Ext4、XFS、Btrfs 及网络文件系统 (NFS) 等多种格式，Linux 内核在用户程序和具体文件系统之间引入了**虚拟文件系统 (VFS)** 作为抽象层。

- **对用户**：应用程序通过统一的系统调用 (`open`, `read`, `write`) 操作文件，无需关心底层文件系统类型。
- **对内核**：VFS 将通用操作翻译成具体文件系统的实现，屏蔽了底层差异，极大简化了文件系统的扩展和维护。

[![虚拟文件接口](21.存储管理/虚拟文件接口.png)](https://git.inmind-lab.com/aaronxu/Linux-book/src/branch/main/01.Linux基础/09.存储管理/虚拟文件接口.png)

# 10. 软硬方式链接🔗

- 在 Linux 中，链接（Link）是一种让多个文件名指向同一份数据的机制。主要分为硬链接和软链接两种。

#### 硬链接 (Hard Link)

- **本质**：硬链接是**同一个 inode 的多个文件名**。系统不为其分配独立的 inode，因此硬链接文件与原始文件本质上是同一个文件，只是名称不同。
- **链接计数**：每创建一个硬链接，文件的 inode 链接数就会加 1。只有当链接数减至 0 时，文件的数据块才会被真正释放。因此，即便原始文件被删除，通过剩余的硬链接依然可以访问数据。
- **核心限制**：
  - **不能跨文件系统**：因为不同文件系统的 inode 编号各自独立。
  - **不能链接目录**：为避免目录树出现循环引用，此操作通常被禁止。

#### 软链接 (Symbolic Link)

- **本质**：软链接是一个**独立的特殊文件**，拥有自己全新的 inode。其内部存储的是所链接文件的路径名，类似于 Windows 系统中的“快捷方式”。
- 使用的是**相对路径**
- **特性**：
  - **可跨文件系统**：因为它只存储路径字符串。
  - **可链接目录**。
  - **依赖目标**：如果原始文件被删除或移动，软链接将失效，成为“悬空链接”或“断链”，访问时会提示 `No such file or directory`。

## 10.1 ln

用于创建链接文件

```
ln [选项] 目标
```

**常用参数**

| 参数 | 作用                                                         |
| ---- | ------------------------------------------------------------ |
| `-s` | **创建符号链接**（软链接）。如果不带此参数，则默认创建硬链接。 |
| `-f` | **强制创建**。如果目标文件已存在，则先删除再创建。           |
| `-i` | **交互式操作**。在覆盖已存在的目标文件前，会提示用户确认。   |
| `-v` | **显示详细信息**。在执行操作时，输出创建过程。               |

## 11.1 认识分布式存储

**🗄️ 什么是分布式存储？**

简单来说，分布式存储是一种数据存储技术，它**通过网络将分散的存储资源（如硬盘、服务器）连接起来，并作为一个整体来进行管理和使用**。数据被切分后，存储在多台独立的设备上。

**🎯 解决了什么问题？**

分布式存储主要解决了传统集中式存储在容量、性能、可靠性和成本上的瓶颈。

- **海量数据存储**

  解决了单机存储容量有限的问题。当数据增长到TB、PB甚至EB级别时，单机无法容纳，分布式存储可以通过增加节点实现近乎无限的横向扩展。

- **高并发访问**

  解决了单机I/O性能瓶颈。通过将数据分片并分散存储，大量客户端可以同时从不同节点读写数据，从而提供远超单机系统的聚合带宽和IOPS。

- **高可靠性**

  解决了单机故障导致数据丢失的风险。通过数据冗余（如副本、纠删码）技术，即使部分节点或硬盘损坏，数据依然完整，服务不中断。

- **低成本与弹性**

  解决了专用硬件成本高昂的问题。分布式存储通常基于通用x86服务器和标准网络设备构建，避免了昂贵的专用硬件（Scale-up），通过增加普通节点即可实现扩容（Scale-out），更具性价比。

**🚀 为什么会出现分布式存储？**

分布式存储的出现是数据时代发展的必然结果，主要受以下因素驱动：

1. **数据规模的爆炸式增长**

   互联网、物联网、大数据等业务产生的数据量远超单机处理能力，传统存储架构在容量和性能上无法满足需求。

2. **对系统可用性的极致追求**

   7x24小时不间断服务成为常态。分布式系统通过冗余设计，确保了单点故障不影响整体服务，这是单机存储无法比拟的。

3. **成本效益的考量**

   使用大量廉价的通用服务器构建存储集群，比购买高端专用存储设备（如大型机、高端SAN）的成本要低得多，尤其适合大规模部署。

## 12.1 块存储

**💾 什么是块存储？**

块存储（Block Storage）是一种将数据以**固定大小的“块”（Block）**为单位进行存储和管理的存储技术。在块存储系统中，数据被分割成大小相同的块，每个块被赋予一个唯一的地址，然后被分散存储到不同的物理磁盘上。操作系统（OS）通过文件系统（如 ext4, XFS）将块组织成一个个完整的文件。

> **核心特点**：块存储设备对外表现为一个**原始的、未格式化的硬盘**，用户可以自由地在其上创建任意类型的文件系统。

**🔧 块存储的工作原理**

1. **数据分块**：当上层应用（如数据库、虚拟机）写入数据时，数据被切分成固定大小的块（如 4KB）。
2. **地址寻址**：每个块都有一个独立的逻辑地址（LBA），操作系统通过这个地址来读写数据，而不是通过文件名。
3. **逻辑卷管理**：通过 RAID 或 LVM（逻辑卷管理）等技术，将多个物理硬盘或块设备组合成一个大的逻辑卷，提供给用户使用。

**✅ 块存储的优点**

- **极致性能**：数据直接通过 SCSI, iSCSI, FC 等协议读写，没有额外的文件系统开销，延迟极低，IOPS（每秒读写次数）极高。
- **灵活可控**：用户拥有设备的完全控制权，可以自由选择文件系统类型（如 ext4, XFS, ZFS），并进行精细的格式化配置。
- **广泛兼容**：是几乎所有操作系统（Linux, Windows 等）的原生支持存储类型，应用兼容性最好。

**❌ 块存储的缺点**

- **无共享**：多个客户端无法直接同时挂载同一个块设备并协调写入，否则会导致数据损坏。需要配合集群文件系统（如 GFS2, OCFS2）才能实现共享。
- **容量限制**：单个块设备的容量受限于后端存储系统的配置，扩容通常需要停机或复杂的操作。
- **管理复杂**：对于大规模、跨地域的共享数据场景，块存储的管理和维护成本较高。

**🚀 主要应用场景**

块存储非常适合对性能和延迟敏感，且不需要多节点共享写的场景。

- **数据库**：如 MySQL, Oracle, PostgreSQL。数据库的日志和数据文件需要极高的 IOPS 和低延迟，块存储是首选。
- **虚拟化/云平台**：如 VMware, OpenStack, 阿里云 ECS。虚拟机的系统盘和数据盘通常以块设备（如云硬盘）的形式提供。
- **高性能计算 (HPC)**：需要高速读写大量数据的科学计算和工程模拟场景。

## 12.2 文件存储

**📁 什么是文件存储？**

文件存储（File Storage）是一种**基于文件和目录层级结构**的数据存储方式。它通过**网络附加存储（NAS）**协议（如 NFS、SMB/CIFS）为客户端提供标准的文件系统视图，使用户可以像访问本地文件夹一样，通过路径（如 `/home/user/data`）来存取数据。

> **核心特点**：对外呈现为一个**挂载点**，支持多客户端通过标准协议进行**共享访问**。

**🏗️ 文件存储的架构**

典型的文件存储架构包含一个**控制平面**（元数据服务）和一个**数据平面**（数据存储服务）。

1. **元数据服务 (Metadata Service)**：管理文件系统的命名空间、目录结构、权限和属性。这是文件存储的“大脑”。
2. **数据存储服务 (Data Service)**：实际存储文件内容和数据块。数据通常被打散存储在多个节点上以实现冗余和性能提升。

客户端通过挂载协议（如 NFSv3/v4, SMB）连接到存储集群，由客户端内核或用户态库（如 FUSE）将文件操作转换为网络请求发送给存储集群。

**✅ 文件存储的优点**

- **易于使用和共享**：提供标准的文件系统接口（POSIX 兼容），开发者和运维人员无需修改应用即可直接使用。支持多客户端并发读写，非常适合需要共享数据的场景（如代码仓库、日志分析）。
- **强大的数据管理**：支持丰富的文件属性（权限、ACL、时间戳），便于进行细粒度的访问控制和数据生命周期管理（分层、归档）。
- **良好的扩展性**：分布式文件存储（如 CephFS, GlusterFS）可以通过增加节点来扩展容量和吞吐量，适应数据增长。

**❌ 文件存储的缺点**

- **性能瓶颈**：所有文件操作都需要经过元数据服务，在高并发场景下容易成为性能瓶颈。网络延迟和协议开销也会降低 IOPS 和吞吐量。
- **单点故障风险**：传统的中心化元数据服务存在单点故障风险。虽然现代分布式系统通过多副本和主备机制解决了此问题，但架构上更为复杂。

**🚀 主要应用场景**

文件存储适用于需要共享访问、目录结构清晰且对性能要求不是极端苛刻的场景。

- **共享工作区**：如企业内部的共享网盘、部门文件服务器、代码仓库（Git/SVN）后端存储。
- **媒体处理**：如视频编辑、图像处理、音频制作，需要多台工作站并发访问同一个素材库。
- **大数据分析**：作为 Hadoop、Spark 等计算框架的输入/输出数据源，提供统一的数据视图。
- **备份与归档**：用于集中存储备份数据、日志文件和冷数据，便于统一管理。

## 12.3 对象存储

**对象存储 (Object Storage)**

对象存储是一种**扁平化**、**基于HTTP协议**的数据存储架构。它将数据和元数据打包成一个个独立的“对象”，存储在一个无层次结构的“桶”（Bucket）中。每个对象通过一个全球唯一的ID进行访问，而非传统的文件路径。

> **核心特点**：**非层次化、海量扩展、HTTP接口**。它不关心底层的文件系统或块设备细节，专为海量非结构化数据（图片、视频、日志、备份）的存储和管理而设计。

**🏗️ 对象存储的架构**

对象存储通常采用**去中心化**或**分布式哈希表 (DHT)** 架构，以实现极高的可扩展性。

1. **数据平面 (Data Plane)**：对象被切分成多个分片（Chunks），并通过**纠删码 (Erasure Coding)** 或**多副本**技术分散存储在成千上万个节点上，确保数据的高可靠性和持久性。
2. **元数据平面 (Metadata Plane)**：元数据（如对象名、大小、创建时间、自定义标签）与对象数据分离存储，通常通过专用的数据库或索引服务进行管理，以支持快速检索。
3. **接入层 (Access Layer)**：提供统一的 **RESTful API** 接口（如 AWS S3, OpenStack Swift），客户端通过HTTP/HTTPS协议进行数据的上传、下载和管理。

**✅ 对象存储的优点**

- **近乎无限的扩展性**：采用扁平化结构，没有目录树深度的限制，理论上可以存储数十亿甚至数万亿个对象，容量可达EB级别。
- **极高的数据持久性**：通过纠删码或多副本机制，数据被分散存储，即使多个节点或硬盘发生故障，数据也不会丢失。
- **低成本**：硬件通常为标准的x86服务器，无需昂贵的专有硬件，且纠删码技术比多副本更节省存储空间，降低了每GB的成本。
- **易于访问和管理**：提供标准的HTTP API，任何能联网的设备（手机、服务器、IoT设备）都可以轻松上传和下载数据，非常适合跨地域、跨平台的应用。

**❌ 对象存储的缺点**

- **不适合频繁修改**：对象存储设计为“**一次写入，多次读取**”，修改一个对象通常需要完整的覆盖重写，不适合需要频繁更新和随机写入的场景（如数据库）。
- **高延迟**：基于HTTP协议，且需要经过元数据查询和数据路由，访问延迟远高于块存储和文件存储，不适合对延迟极其敏感的业务。
- **无原生文件语义**：不支持文件锁、硬链接、POSIX权限等高级文件系统特性，无法直接挂载为本地磁盘使用。

**🚀 主要应用场景**

对象存储是云计算时代的基石，广泛应用于以下场景：

- **静态网站托管**：直接通过HTTP服务HTML、CSS、JS和图片等静态资源。
- **海量数据备份与归档**：如数据库备份、日志归档、冷数据长期保存，利用其高持久性和低成本特性。
- **内容分发网络 (CDN) 源站**：作为图片、视频等富媒体内容的原始存储，通过CDN加速全球分发。
- **大数据分析**：作为数据湖（Data Lake）的底层存储，存储海量的原始日志、传感器数据等，供Hadoop、Spark等计算框架进行分析。
- **云原生应用**：作为Kubernetes等平台的持久化存储，用于存储应用产生的非结构化数据。

## 12.4 各类存储差异

**🗂️ 各类存储差异总结**

存储的世界主要分为三大流派：**块存储**、**文件存储**和**对象存储**。

为了方便记忆，你可以把它们想象成不同的“容器”：

- **块存储** 像一块**空白硬盘**，速度快但需要自己格式化。
- **文件存储** 像一块**公共网盘**，大家都能看，有目录结构。
- **对象存储** 像一个大号的**网盘备份箱**，东西往里一扔拿链接，无限扩容。

**📊 多维度对比一览**

下表清晰地展示了三者在核心特性上的差异：

| 特性         | 🚀 块存储 (Block Storage)   | 📁 文件存储 (File Storage)   | ☁️ 对象存储 (Object Storage)           |
| ------------ | -------------------------- | --------------------------- | ------------------------------------- |
| **核心概念** | 裸磁盘、卷                 | 目录、文件夹                | 桶 (Bucket)、对象 (Object)            |
| **数据结构** | 扁平的块 (无固定格式)      | 树状的层级结构 (目录树)     | 扁平的命名空间 (无目录概念)           |
| **访问方式** | 挂载为本地磁盘 (iSCSI, FC) | 挂载为网络驱动器 (NFS, SMB) | HTTP/HTTPS 接口 (RESTful API)         |
| **典型协议** | SCSI, iSCSI, FC            | NFS, SMB/CIFS               | S3, Swift                             |
| **写入方式** | 直接写入扇区               | 通过文件系统接口            | PUT/POST 请求上传                     |
| **数据共享** | **不支持** (单主机独占)    | **支持** (多主机并发读写)   | **支持** (多主机通过API访问)          |
| **性能**     | **极高** (低延迟, 高IOPS)  | **中等** (受网络和协议影响) | **较高吞吐量** (适合大文件, 延迟较高) |
| **容量扩展** | 较难 (需LVM扩展)           | 中等 (可在线扩容)           | **无限扩展** (理论上EB级)             |
| **成本**     | 昂贵 (硬件成本高)          | 中等                        | **廉价** (利用通用服务器)             |
| **适用场景** | 数据库、虚拟机系统盘       | 企业共享盘、开发环境        | 图片视频、备份归档、大数据            |

**🎯 如何快速选择**？

根据以下口诀，你可以快速判断该用哪种存储：

1. **看业务类型**
   - **结构化数据 (数据库、ERP)**：首选 **块存储**。因为数据库需要极致的随机读写性能和低延迟，块存储能提供裸设备的性能。
   - **非结构化数据 (图片、视频、日志)**：首选 **对象存储**。因为这类数据量大，需要长期保存且读取频繁，对象存储成本低且扩展性强。
   - **需要多人协作 (办公文档、代码)**：首选 **文件存储**。因为大家习惯通过文件夹路径访问，且需要多台机器同时读写。
2. **看访问接口**
   - **需要挂载本地路径 (`/mnt/data`)**：选 **块存储** 或 **文件存储**。
   - **需要调用 API (`PUT / GET`)**：选 **对象存储**。
3. **看规模与成本**
   - **数据量 < 100TB，预算充足**：块/文件存储足够。
   - **数据量 > PB级，追求低成本**：必须上 **对象存储**。

## 13.1 ceph概念

Ceph 是一个**统一的、高可靠、高扩展的分布式存储系统**，底层基于 **RADOS**（Reliable Autonomic Distributed Object Store）分布式对象存储，对外同时提供**块存储（RBD）、文件系统（CephFS）、对象存储（RGW）** 三种服务。

![ceph集群架构](21.存储管理/0455d2982cf49bd6116dd3ce12e2b412tplv-be4g95zd3a-image.jpeg)

### 13.1.1 核心概念

#### 13.1.1.1 RADOS

Ceph 底层核心，**分布式对象存储系统**，所有数据最终以 **Object（对象）** 形式存储在 OSD 上。

- 无中心架构，用 **CRUSH 算法** 做数据分布与定位
- 自带**副本 / 纠删码、故障检测、自动恢复、数据重平衡**
- 是 RBD/CephFS/RGW 三种服务的基础

#### 13.1.1.2 Object（对象）

- Ceph 最小存储单元：**数据 + 元数据 + 唯一 ID**
- 大小通常 4MB/8MB/16MB（可配置）
- 文件 / 块 / 对象上层数据都会被切分为 Object 存入 RADOS

#### 13.1.1.3 Pool（存储池）(相当于开一个百度网盘账号，分配内存)

- 逻辑分区：**命名空间 + 数据策略**集合
- 定义：**副本数、PG 数量、CRUSH 规则、数据类型（数据 / 元数据）**
- 不同服务（RBD/CephFS/RGW）建议用独立 Pool

#### 13.1.1.4 PG（Placement Group）

- **中间逻辑层**：一组 Object 的集合
- 作用：减少 OSD 元数据开销、提升数据分布均衡性
- 一个 PG 会映射到 N 个 OSD（副本数决定 N）

#### 13.1.1.5 CRUSH 算法

- 伪随机数据分布算法：**无中心查表**
- 输入：Object ID + Pool ID + CRUSH Rule → 输出：目标 OSD 列表
- 支持**机架 / 机房 / 主机**级故障域隔离

### 13.1.2 Ceph 核心组件

#### 13.1.2.1 Monitor（MON）— 集群大脑

**作用**

- 维护集群**全局状态与一致性**（Paxos 仲裁）
- 存储 4 张 Map：**Mon Map、OSD Map、PG Map、CRUSH Map**
- 集群认证、服务发现、健康检查、配置管理
- 保证**无单点故障**：通常部署 **3/5 奇数节点**

**关键参数与调整影响**

- `mon_clock_drift_allowed`：时钟偏差容忍度（默认 0.05s）
  - 调大：容忍更大时钟差 → **集群更稳，但一致性风险上升**
  - 调小：时钟更严格 → **易出现 HEALTH_WARN/ERR，服务中断**
- `mon_osd_down_out_interval`：OSD 下线多久标记为 out（默认 300s）
  - 调大：故障判定变慢 → **恢复慢，但抖动减少**
  - 调小：快速判定故障 → **立即触发恢复，IO 波动大**
- `mon_paxos_proposer_timeout`：Paxos 提案超时
  - 调大：网络差时更稳 → **收敛慢，配置更新延迟**
  - 调小：收敛快 → **网络抖动易失败，集群不稳定**

#### 13.1.2.2 OSD（Object Storage Daemon）— 数据存储核心

**作用**

- 真正**存储数据对象**（BlueStore/FileStore）
- 数据**副本同步、故障恢复、数据回填、重平衡**
- 心跳上报状态、响应客户端 IO
- 每个 OSD 通常对应**一块物理盘**

**关键参数与调整影响**

- `osd_pool_default_size`：默认副本数（默认 3）
  - 调大：**数据更安全** → 可用容量下降、网络 / IO 负载上升
  - 调小：**容量提升、性能提升** → 可靠性下降（丢盘风险高）
- `osd_recovery_max_active`：单 OSD 最大并发恢复（默认 3）
  - 调大：**恢复更快** → 业务 IO 延迟飙升、集群不稳定
  - 调小：**业务优先** → 恢复慢、数据冗余不足风险
- `osd_op_threads`：OSD 工作线程（默认 1）
  - 调大：**高并发 IO 更快** → CPU 占用高、上下文切换开销大
  - 调小：CPU 省 → **高并发时队列阻塞、延迟高**
- `bluestore_compression_algorithm`：BlueStore 压缩算法（lz4/zstd）
  - 开启 lz4：**节省空间（1.2–2 倍）、低 CPU 开销**
  - 开启 zstd：**压缩比更高** → 读写延迟增加、CPU 高
- `osd_memory_target`：OSD 内存上限（默认 4GB）
  - 调大：**缓存更大、读性能更好** → 内存占用高、OOM 风险
  - 调小：内存省 → **缓存命中率低、读性能差**
- `pg_num / pgp_num`：PG 数量
  - 太少：**数据不均、OSD 热点、恢复慢**
  - 太多：**内存暴涨、心跳压力大、扩缩容极慢**
  - 推荐：`OSD总数 × (100–300) / 副本数 / 池数`

#### 13.1.2.3 Manager（MGR）— 集群管家

**作用**

- 监控指标、Dashboard、REST API、CLI 增强
- 负载均衡、自动化调度、状态统计
- 模块：Prometheus、Zabbix、Balancer、Dashboard 等

**调整影响**

- 启用 `mgr balancer`：自动数据均衡 → **后台 IO 增加、业务延迟微升**
- 关闭 MGR：**Dashboard / 监控失效**，但不影响数据 IO

#### 13.1.2.4 RGW（RADOS Gateway）— 对象存储网关

**作用**

- 提供 **S3/Swift 兼容**的对象存储接口
- 用户 / 桶 / 权限管理、配额、地域复制

**调整影响**

- `rgw_thread_pool_size`：RGW 线程数
  - 调大：**并发更高** → CPU / 内存占用上升
  
- `rgw_max_concurrent_requests`：最大并发请求

  - 调大：**高并发强** → 队列长、延迟上升

#### 13.1.2.5 RBD（RADOS Block Device）— 块存储

**作用**

- 提供**分布式块设备**（云硬盘、虚拟机磁盘）
- 快照、克隆、增量备份、扩容

**调整影响**

- `rbd_cache`：开启客户端缓存
  - 开启：**随机读性能大幅提升** → 数据一致性风险（断电丢缓存）
- `rbd_cache_size`：客户端缓存大小
  - 调大：**读性能更好** → 客户端内存占用高

### 13.1.3 CephFS 文件系统专用组件

CephFS = **MDS（元数据） + 数据 Pool（RADOS）**，提供 **POSIX 兼容分布式文件系统**Ceph。

#### 13.1.3.1 MDS（Metadata Server）— 元数据服务器

**作用**

- 管理**文件系统命名空间**：目录、文件名、权限、inode、属性
- 处理 `open/stat/readdir/rename/unlink` 等元数据操作
- 元数据缓存、分布式分片、负载均衡
- 数据 IO 不经过 MDS（直接客户端 ↔ OSD）

**关键参数与调整影响**

- `mds_cache_size`：MDS 元数据缓存（默认 1GB）
  - 调大：**元数据操作极快** → 内存暴涨、大目录卡顿风险
  - 调小：内存省 → **缓存频繁淘汰、stat/readdir 慢**
- `mds_max_completed_requests`：完成请求缓存数
  - 调大：**重入 / 重试更快** → 内存占用高
- `mds_beacon_interval`：MDS 心跳间隔（默认 1s）
  - 调大：**网络 / CPU 省** → 故障检测慢、切换慢
  - 调小：故障切换快 → **心跳开销大**
- `mds_standby_for_rank`：Standby 热备
  - 开启：**MDS 故障秒级切换** → 额外资源占用
- `mds_cache_mid`：缓存淘汰阈值
  - 调大：**缓存更积极** → 内存占用高、GC 频繁

#### 13.1.3.2 CephFS 双 Pool 结构

- fs_metadata Pool：存 inode、目录、权（低容量、高 IOPS、低延迟）
  - 建议：**SSD、副本 3、小 PG 数量**
- fs_data Pool：存文件内容（大容量、高吞吐）
  - 建议：**HDD/SSD、副本 3 / 纠删码、PG 合理**

### 13.1.4 组件关系与整体架构

- **MON**：维护集群地图与一致性
- **OSD**：存数据、副本、恢复、IO
- **MGR**：监控、Dashboard、调度
- **MDS**：仅 CephFS 用，管元数据
- **RBD/RGW/CephFS**：上层接口，基于 RADOS

### 13.1.5 调整原则总结

- **MON**：**优先稳定**，时钟 / 超时不要激进
- **OSD**：**业务 IO 与恢复平衡**，恢复参数高峰期调低
- **PG**：**一次算好、分批调整**，严禁频繁改
- **MDS**：**内存给够**，元数据性能决定文件系统体验
- **副本数**：**生产 3 副本**，容量与安全平衡
- **压缩**：**BlueStore 开 lz4**，空间与性能平衡

- osd维护操作

```bash
# 先将 OSD 标记为 out，Ceph 会自动迁移该 OSD 上的数据到其他 OSD，避免数据丢失
# 标记单个 OSD 为 out（如 osd.0）
ceph osd out osd.0

# 批量标记（如 osd.0、osd.1）
ceph osd out osd.0 osd.1

# 停止 OSD（如 osd.0）
ceph orch daemon stop osd.0

# 启动 OSD
ceph orch daemon start osd.0

# 重启 OSD
ceph orch daemon restart osd.0

# 重启节点上所有 OSD（如 node01）
ceph orch daemon restart osd --host node01

# OSD 标记为「in」（维护完成后恢复）
ceph osd in osd.0

# # 设置 OSD 权重（如 osd.0 权重为 1.0，默认 1.0）
ceph osd crush set osd.0 1.0 host=node01

# 查看 OSD 权重
ceph osd crush tree

# 安全删除 OSD（推荐）
# 步骤 1：标记 OSD 为 out（迁移数据）
ceph osd out osd.0

# 步骤 2：停止 OSD 进程
ceph orch daemon stop osd.0

# 步骤 3：从集群中删除 OSD
ceph osd rm osd.0

# 步骤 4：删除 OSD 认证密钥（可选，清理残留）
ceph auth del osd.0

# 步骤 5：从 CRUSH 映射中移除 OSD
ceph osd crush rm osd.0

# 强制删除 OSD（紧急场景，慎用）
ceph osd rm osd.0 --force
```
