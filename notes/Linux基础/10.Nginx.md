# 1.Nginx安装

## 1.1 编译安装

- Nginx编译安装相比yum安装在安全性方面有以下主要优势：

1. **版本控制更灵活**
- **获取最新安全补丁**：可以立即安装包含安全修复的最新版本，无需等待仓库更新
  
- **避免旧版本漏洞**：yum仓库中的版本可能滞后，存在已知漏洞
  
- **长期支持版本选择**：可以选择特定LTS版本，获得更长的安全支持周期


2. **模块定制化**
- **仅安装必要模块**：减少攻击面，移除不需要的功能模块
   - **安全模块集成**：可编译加入安全增强模块如：
     - `ngx_http_headers_module`（安全头设置）
     - `ngx_http_limit_req_module`（请求限制）
     - 第三方安全模块（ModSecurity等）
   
- **禁用危险模块**：排除可能带来风险的模块


3. **编译选项安全加固**

```bash
# 示例安全编译选项
./configure \
  --with-cc-opt="-O2 -g -pipe -Wall -Wp,-D_FORTIFY_SOURCE=2 -fexceptions" \
  --with-ld-opt="-Wl,-z,relro,-z,now" \
  --prefix=/usr/local/nginx \
  --user=nginx \
  --group=nginx \
  --with-http_ssl_module \
  --with-http_realip_module \
  --with-http_stub_status_module \
  --without-http_autoindex_module  # 禁用目录列表
```

4. **运行环境更安全**
- **非特权用户运行**：可指定专用低权限用户
  
- **自定义安装路径**：避免标准路径被攻击者预测
  
- **文件权限控制**：精细设置配置文件和日志权限


5. **安全特性启用**

   - **TLS优化**：启用最新TLS版本和加密套件

   - **安全头支持**：完整的安全响应头功能

   - **连接限制**：内置防护DDoS攻击的模块


6. **依赖管理**

   - **可控的依赖版本**：自行选择依赖库版本，避免仓库中的老旧依赖

   - **安全补丁应用**：及时为依赖库打补丁


- 对比表格

| 特性         | 编译安装     | Yum安装      |
| ------------ | ------------ | ------------ |
| 版本时效性   | 立即获取最新 | 有延迟       |
| 模块定制     | 完全可控     | 固定集合     |
| 安全加固选项 | 可深度定制   | 有限         |
| 依赖控制     | 自主管理     | 仓库管理     |
| 更新速度     | 即时         | 依赖仓库更新 |

- 实际建议：

  - **适合编译安装的场景**：

    - 对安全性要求高的生产环境

    - 需要特定安全模块

    - 希望快速应用安全补丁

    - 有专业运维团队


  - **适合yum安装的场景**：

    - 快速部署测试环境

    - 小型项目或内部系统

    - 缺乏专业运维资源

    - 需要自动依赖管理


  - 编译安装虽然安全性更高，但需要更多的维护工作。最佳实践是：**生产环境使用编译安装并建立自己的更新流程，开发测试环境可使用yum安装提高效率**。

# 5. Location

- Nginx 的 location 指令是配置请求路由的核心机制，其匹配规则基于 **URI** 和**修饰符**，优先级由匹配类型和顺序共同决定。

  ```shell
  location [ = | ~ | ~* | ^~ ] uri { ... }
  ```

  | 修饰符   | 匹配类型 | 语法示例                | 说明                                             |
  | -------- | -------- | ----------------------- | ------------------------------------------------ |
  | =        | 精确匹配 | location = /path        | 仅当 URI 完全等于 /path 时匹配，优先级最高       |
  | ^~       | 前缀匹配 | location ^~ /images/    | 匹配以 /images/ 开头的 URI，停止后续正则检查     |
  | ~        | 正则匹配 | location ~ .php$        | 区分大小写，正则表达式匹配，按配置文件顺序匹配   |
  | ~*       | 正则匹配 | location ~* .(jpg,png)$ | 不区分大小写，正则表达式匹配，按配置文件顺序匹配 |
  | 无修饰符 | 前缀匹配 | location /static/       | 匹配以 /static/ 开头的 URI，需继续正则检查       |
  | /        | 通用匹配 | location /              | 匹配所有请求，优先级最低                         |

- **优先级**：`= ^~ ~/~* 无修饰符 /`

- 常用变量

```bash
$remote_addr;
# 存放了客户端的地址，注意是客户端的公网IP
$proxy_add_x_forwarded_for;
# 此变量表示将客户端IP追加请求报文中X-Forwarded-For首部字段，多个IP之间用逗号分隔，如果请求中没有X-Forwarder-For，就使用$remote_addr
$args;
# 变量中存放了URL中的参数
$document_root;
# 保存了针对当前资源的系统根目录
$document_uri;
# 保存了当前请求中不包含参数的URI,注意是不包含请求的指令，比如/img/logo.png
$host;
# 存放了请求的host名称
limit_rate 10240;
echo $limit_rate;
# 如果nginx服务器使用limit_rate配置了显示网络速率，则会显示，如果没有设置，则显示0
$remote_port;
# 客户端请求Nginx服务器时随机打开的端口，这是每个客户端自己的端口
$remote_user;
# 已经经过Auth Basic Module验证的用户名
$request_body_file;
# 做反向代理时发给后端服务器的本地资源的名称
$request_method;
# 请求资源的方式，GET/PUT等等
$request_filename;
# 当前请求的资源文件的磁盘路径，由root或alias指令与URL请求生成的文件绝对路径
# /apps/nginx/html/www/index.html
$request_uri;
# 包含请求参数的原始URI,不包含主机名，相当于:$document_uri?$args
$scheme;
# 请求的协议，例如：http,https,ftp等等
$server_protocol;
# 保存了客户端请求资源使用的协议版本，例如：HTTP/1.0,HTTP/1.1,HTTP/2.0等等
$server_addr;
```

## 12.0 Nginx 架构和进程

### 12.0.1 Nginx架构

Nginx 采用了 master-worker 架构，由 master 进程负责通信和调度，worker 进程响应具体的请求

![image-Nginx架构](10.Nginx/Nginx架构.png)

### 12.0.2 Nginx进程模型

Nginx 的进程模型是其高性能和高并发的核心，采用多进程架构（默认模式），主要由 Master 进程和多个 Worker 进程组成，结合**异步非阻塞 I/O 模型**实现高效请求处理

[![image-Nginx进程模型](10.Nginx/Nginx进程模型.png)](https://git.inmind-lab.com/aaronxu/Linux-book/src/branch/main/02.企业服务/05.Nginx/Nginx进程模型.png)

**Master 进程:**

- 对外接口：接收外部的操作(信号)
- 对内转发：根据外部的操作的不同，通过信号管理 worker
- 监控：监控 worker 进程的运行状态，worker 进程异常终止后，自动重启 worker 进程
- 配置加载：读取 Nginx 配置文件并验证其有效性和正确性
- 管理连接：建立、绑定和关闭 socket 连接
- 按照配置生成、管理和结束工作进程
- 接受外界指令，比如重启、升级及退出服务器等指令
- 不中断服务，实现平滑升级，重启服务并应用新的配置
- 开启日志文件，获取文件描述符
- 不中断服务，实现平滑升级，升级失败进行回滚处理

**Worker 进程:**

- 所有 Worker 进程都是平等的，接受处理客户的请求
- 实际处理：网络请求，由 Worker 进程处理
- Worker进程数量：在nginx.conf 中配置，一般设置为核心数，充分利用 CPU 资源，同时，避免进程数量过多，避免进程竞争 CPU 资源，增加上下文切换的损耗。
- 将请求依次送入各个功能模块进行处理
- I/O调用，获取响应数据
- 与后端服务器通信，接收后端服务器的处理结果
- 缓存数据，访问缓存索引，查询和调用缓存数据
- 发送请求结果，响应客户的请求
- 接收主程序指令，比如重启、升级和退出等

**信号**：Master 进程通过信号控制 Worker 进程的生命周期及配置更新，典型场景：SIGHUP（重新加载配置文件）、SIGTERM（优雅关闭 Worker 进程）、SIGUSR1（重新打开日志文件） **管道**：Master 进程与 Worker 进程之间单向传递指令，Master 进程传递 Worker ID、指令、索引、文件描述符等等，Worker 进程监听管道事件并执行具体事项 **共享内存**：Worker 进程间共享数据，典型场景：限流计数、缓存状态等等

## 12.2 工作优先级

- 调整worker进程的优先级(nice值)
  - nice可以影响CPU调度时间周期
  - -20是最高优先级，19是最低优先级，0是默认
- 调整每个Worker能打开的文件数
  - 由于Linux中一切皆文件，所以各种连接也都是文件，最大文件打开数会影响并发
  - 调整系统的limits，才可以让nginx配置文件中`worker_rlimit_nofile`生效

```bash
worker_priority 0;   #工作进程优先级(-20~19)
#所有worker进程能打开的文件数量上线，
#包括：Nginx的所有连接(例如与代理服务器的连接等)，而不仅仅是与客户端的连接，
#另一个考虑因素是实际的并发连接数不能超过系统级别的最大打开文件数的限制，最好与ulimit -n的值保持一致
worker_rlimit_nofile 65536;     
[root@localhost ~]# vim /etc/security/limits.conf
*        soft    nofile    102400
*        hard    nofile    102400


# 案例-修改优先级
```

# 13. LNMP架构

- LNMP是一套技术的组合，L=Linux、N=Nginx、M=MySQL、P=PHP

- 首先 nginx 服务是不能处理动态请求，那么当用户发起动态请求时，nginx 无法处理

## 14.2 代理路径问题

- 在`proxy_pass`后面的路径是否以`/`结尾是有区别的

| `proxy_pass`地址格式      | 请求 URI 拼接规则                                            | 通俗理解                                   |
| ------------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| **不以** **`/`** **结尾** | 保留`location`匹配的完整路径，将`location`匹配部分 + 后续 URI 拼接到代理地址后 | 代理地址**拼接完整请求路径**               |
| **以** **`/`** **结尾**   | 剔除`location`匹配的路径，仅将`location`后的剩余 URI 拼接到代理地址后 | 代理地址**替换****`location`****匹配部分** |

- 如果location使用正则匹配（~ ~*），proxy_pass 结尾是否加 / 完全无效，Nginx 会忽略location匹配的内容，直接将完整请求 URI拼接到proxy_pass后。

# 15. 网络基础

## 15.1 OSI七层模型

- 由ISO组织制定的一套数字通信标准流程模型，这个模型是一个建议模型，不是强制的。
- 七层模型从高到低
  - 应用层
    - 提供用户的交互接口
  - 表示层
    - 提供数据的编码解码，压缩解压缩，加密解密等处理
  - 会话层
    - 提供会话ID，会话管理
  - 传输层
    - 提供数据的分段，提供具体传输方式，在应用数据前加上TCP/UDP的头部，此层叫做数据段
    - TCP
      - 可靠传输，使用序列号和确认号来确保每个数据都被正确的接受
      - 应用层不需要制定额外的机制，就可以保障数据的准确传输
      - TCP需要有额外的网络开销
    - UDP
      - 不可靠传输，数据不分段，单个的数据不能超过MTU限制
      - 发送后，无法获取到对方是否成功无误的接受
      - 使用UDP如果需要可靠传输，需要应用层面制定额外的机制保障
    - 端口号
      - 将数据与应用的进程号进行绑定
      - 区分电脑上的不同网络应用
      - 源和目的端口号
      - 端口号范围：1-65535
      - 1-1024是预留给公用服务的
        - 80 http
        - 443 https
        - 445 smb
        - 22 ssh
        - 53 dns
        - 23 telnet
        - 3306 mysql
        - 3389 windows远程桌面
  - 网络层
    - 最大传输单元，一个网络数据包常见最大是1500字节，叫做MTU，此层叫做数据包
    - 提供了远程访问的IP地址寻址功能，相当于门牌号码，可以帮助快递找到你在的大概位置
    - 基本概念
      - 公网IP地址、私有IP地址
      - 子网掩码，用于定义网络位，网络位相同表示同一个局域网
      - 广播地址，是主机位都为1，向此地址发送数据，全部局域网都能收到
      - 网络号，是主机位都为0，此地址无法用于通信，是用来代指此局域网的
    - 源和目的IP地址
  - 数据链路层
    - 提供数据完整性校验，需要保证每一个二进制都是正确的，此层叫做数据帧
      - 使用CRC循环冗余校验算法，将二进制计算得到校验值，此校验值在接受的时候会拿来与新计算的比较，如果一致，说明数据有效
    - 提供物理传输接口的编号(MAC地址)，此地址是烧录在芯片上，无法轻易改变，能够确定具体的设备的具体的接口
    - MAC地址并不是全球唯一的，虚拟机的网卡MAC地址随机产生并可自定义，为了保障通信，在一个局域网中，必须唯一
    - 源和目的mac地址
  - 物理层
    - 定义数据传输介质的电气规范（二级制，数据位）
    - 有线
      - 电缆
      - 光缆
      - 接口类型
        - RJ45 水晶头
        - SC连接器 LC连接器
    - 无线

## 15.2 数据封装

- 物理层
- 数据链路层
  - MAC地址
  - ARP协议
    - 向局域网发送二层的广播（目的mac全是1），查询目的IP地址所对应的MAC地址
    - 收到正确的回应，就会记录在本地的ARP表中，下次再访问就可以直接完成数据的封装
    - ARP表是为了保障局域网内通信的
  - 数据在局域网中，具体是从哪一个设备的什么接口接收，由mac地址决定
  - 在windows或者linuxz中查看arp表的命令`arp -a`
- 网络层
  - IP地址
  - 广播传递的范围仅限于同一个局域网，无法跨越IP网段传播
  - 网络层会维护一个路由表，路由表可以指明去往其他网段应该从什么接口出发，每台具备转发能力的网络层设备，都会查询路由表，然后进行转发，经过多跳之后，数据就可以到达目的地所在的局域网
  - 维护路由表的方法
    - 静态路由，手动把路由表条目写上去
    - 动态路由，通过协议，路由器互相学习
      - OSPF
      - BGP
- 传输层
  - 提供端口号
  - 发送端往往是随机端口号，接收端是常用端口号
- 应用层
  - 端口号对应的进程

- 负载均衡算法

| **调度算法** | **概述**                                                     |
| :----------- | :----------------------------------------------------------- |
| rr 轮询      | 按时间顺序逐一分配到不同的后端服务器(默认)                   |
| weight       | 加权轮询,weight值越大,分配到的访问几率越高                   |
| ip_hash      | 每个请求按访问IP的hash结果分配,这样来自同一IP的固定访问一个后端服务器 |
| url_hash     | 按照访问URL的hash结果来分配请求,使每个URL定向到同一个后端服务器 |
| least_conn   | 最少链接数,哪个机器链接数少少就分发                          |

- 加权轮询

```bash
[root@LB]:~$ cat /etc/nginx/conf.d/node_proxy.conf upstream node {
    server 192.168.73.138:80 weight=2;
    server 192.168.73.139:80;
}
server {
    listen 80;
```

# 17. 负载均衡会话保持

- 什么是会话，http是无状态，如果想要保持登录状态，目前主流的方案
  - cookie
    - 服务器给浏览器发放一个id，并且服务器会找地方存下来这个id以及id对应的数据
    - 登录成功，服务器就会找到浏览器对应的id，并且记录此id已经登陆成功
    - 每次浏览器都需要携带此cookie让服务器可以辨识
  - token
    - 服务器通过私钥将用户的id和登录相关信息进行加密，加密之后存放到客户端上，服务器不需要保存客户端的信息
    - 客户端在访问的时候，带上加密后的信息，服务器使用私钥解密，可以认出客户端的状态
