# 01 Agent 与大模型基础

本章先回答一个最容易被教程跳过的问题：**Agent 到底是什么，它和普通聊天、Chain、Workflow 有什么区别？** 这里不依赖任何大模型 SDK。先看清系统结构，后面使用框架时才不会把“调用一个现成函数”误当成理解了 Agent。

## 学习目标

完成本章后，你应当能够：

1. 区分大语言模型、聊天模型、Chain、Workflow 和 Agent；
2. 解释 Agent 的“观察—决策—行动—再观察”循环；
3. 理解 Token、上下文窗口、推理、采样和幻觉等基础概念；
4. 判断一个需求是否真的需要 Agent；
5. 读懂并运行一个不依赖大模型的最小 Agent 循环；
6. 识别 Agent 的终止条件、步骤上限和权限边界。

## 1. 从模型到 Agent

### 1.1 大语言模型不是完整的 Agent

大语言模型（Large Language Model，LLM）接收一段上下文，并预测接下来最合适的 Token。聊天模型是在 LLM 之上增加了消息角色、对话格式和安全策略的接口形态。

一次普通模型调用可以抽象为：

```text
输入消息 → 模型推理 → 输出消息
```

它本身通常不会自动读取文件、访问数据库、调用天气接口或持续执行任务。让模型具备这些能力，需要在模型外部增加工具、状态、控制循环和安全边界。

### 1.2 Agent 的最小定义

Agent（智能体）是一个能够根据当前目标和状态，选择下一步行动，并利用行动结果继续决策的系统。

```text
目标 + 当前状态
       ↓
    决策器 ──→ 选择行动 ──→ 执行器
       ↑                       ↓
       └────── 新的观察结果 ────┘
```

在大模型 Agent 中，模型常常充当决策器；Python 函数、API、数据库查询等充当工具；应用程序负责真正执行工具、保存状态和控制循环。

> 模型可以“提出要调用什么工具”，但真正执行工具的是宿主程序。模型不应直接获得无限制的系统权限。

## 2. 术语解释

| 术语 | 解释 | 容易混淆的地方 |
| --- | --- | --- |
| LLM | 根据上下文生成 Token 序列的语言模型 | 不等于会自主行动的 Agent |
| Chat Model | 以 system、user、assistant 等消息角色工作的模型接口 | 底层仍是生成模型 |
| Token | 模型处理文本的基本单位，可能是字、词或词的一部分 | Token 数不等于字符数 |
| Context Window | 一次请求中模型能够处理的输入与输出 Token 总预算 | 历史越长不一定越好，还会增加成本 |
| Inference | 使用训练好的模型生成结果的过程 | 不是再次训练模型 |
| Sampling | 按概率选择下一个 Token 的生成过程 | temperature 等参数会影响随机性 |
| Temperature | 调整输出概率分布随机性的参数 | 低温度不保证事实正确 |
| Hallucination | 模型生成了流畅但缺乏依据或事实错误的内容 | 不能只靠“更强 Prompt”彻底消除 |
| Tool | 由程序暴露给 Agent 的可调用能力 | 工具必须有参数校验和权限边界 |
| State | 一次任务执行过程中需要保留的数据 | 不只是聊天记录 |
| Memory | 跨步骤或跨会话保留、检索信息的机制 | 记忆通常是状态的一部分或外部存储 |
| Chain | 按预先确定的顺序组合多个步骤 | 一般不由模型动态决定下一步 |
| Workflow | 含分支、并行、重试等显式流程的任务编排 | 可以包含模型节点，但流程主要由代码定义 |
| Agent | 根据状态动态选择行动的系统 | 自主性越高，成本和风险通常越高 |

## 3. 三类系统的边界

### 3.1 Chain：固定的数据加工管道

```text
用户文本 → 摘要 → 翻译 → 保存
```

步骤已知、顺序固定时，Chain 简单、便宜、容易测试。

### 3.2 Workflow：代码控制的流程

```text
收到工单 → 判断优先级
             ├─ 高：通知值班人员
             └─ 低：进入普通队列
```

Workflow 适合业务规则清楚、需要分支、重试、并行或人工审批的场景。

### 3.3 Agent：运行时动态选择下一步

```text
“分析这份故障报告并给出处理建议”
  → 决定先读报告
  → 发现缺少日志，决定查询日志
  → 发现配置异常，决定读取配置
  → 汇总证据并回答
```

路径无法在开发时完全确定、需要根据中间结果继续选择行动时，才更适合 Agent。

### 3.4 什么时候不该使用 Agent

以下需求通常先用普通代码或 Workflow：

- 输入输出规则明确，可以可靠地写成函数；
- 金额转账、删除数据等高风险动作没有审批机制；
- 对延迟和费用非常敏感；
- 任务只需一次模型调用；
- 每个步骤都必须严格可预测、可证明。

工程上的常见选择是：**确定性流程由代码控制，只把真正需要语言理解或动态决策的局部交给模型。**

## 4. Agent 循环的原理

一个可控的 Agent 循环至少包含六个部分：

1. **目标**：本次任务要完成什么；
2. **状态**：已知信息、历史行动和剩余预算；
3. **观察**：来自用户、工具或环境的新信息；
4. **决策**：选择工具、直接回答或终止；
5. **行动**：由程序执行经过校验的操作；
6. **停止条件**：成功、失败、达到步骤上限或等待人工确认。

伪代码如下：

```python
state = initial_state(goal)

for _ in range(max_steps):
    decision = decide(state)
    if decision.kind == "finish":
        return decision.answer
    observation = execute(decision.action)
    state = update(state, decision, observation)

raise StepLimitExceeded()
```

这里最重要的不是 `for` 循环本身，而是三个边界：

- `decide` 只能产生允许的行动；
- `execute` 必须校验参数、捕获错误并控制权限；
- 循环必须有 `max_steps`，防止死循环和费用失控。

## 5. 递进示例

### 示例 1：固定规则，不需要 Agent

```python
def classify_temperature(value: int) -> str:
    return "hot" if value >= 30 else "comfortable"
```

这只是确定性函数。把它交给模型既更慢，也更不稳定。

### 示例 2：一次决策，也还不是完整 Agent

```python
def choose_action(text: str) -> str:
    if "天气" in text:
        return "lookup_weather"
    return "answer_directly"
```

它已经有“选择动作”的味道，但没有根据执行结果继续决策。

### 示例 3：最小可运行 Agent 循环

运行本章示例：

```powershell
cd AI-agent\01_Agent与大模型基础\examples
python decision_loop.py
```

示例中的决策器是确定性规则，便于离线观察完整循环。后续只需把 `decide` 替换成模型决策，同时保留执行器、状态和安全边界。

关键流程：

```text
用户目标“先查北京温度，再判断是否炎热”
→ 决策：调用 get_temperature
→ 观察：32℃
→ 决策：调用 classify_temperature
→ 观察：炎热
→ 决策：结束并生成答案
```

## 6. 从确定性示例到大模型 Agent

后续模块会逐步替换各部件：

| 当前示例 | 后续实现 |
| --- | --- |
| 字符串目标 | system/user 消息 |
| Python 规则决策器 | 支持工具调用的聊天模型 |
| 普通函数字典 | 带 JSON Schema 的工具定义 |
| 内存中的列表状态 | LangGraph State 与检查点 |
| 固定假数据 | API、数据库、RAG 等真实工具 |
| 终端打印 | API 服务、日志、追踪与评估 |

## 7. 常见错误

### 错误 1：只要使用了大模型就叫 Agent

`prompt → model → text` 是模型应用，不一定是 Agent。判断关键是系统是否会根据状态动态选择并执行行动。

### 错误 2：让模型直接执行任意代码

模型输出属于不可信输入。应将模型选择映射到白名单工具，并对参数、超时、权限和结果大小进行限制。

### 错误 3：没有终止条件

Agent 可能重复调用工具。必须限制最大步骤、最长时间、费用预算，并检测重复行动。

### 错误 4：把所有业务规则都交给模型

金额计算、权限判断、格式校验等确定性逻辑应由代码完成。模型更适合语言理解、信息归纳和开放式决策。

### 错误 5：把聊天记录等同于完整状态

真实状态还可能包含任务 ID、审批状态、已用预算、工具结果、重试次数和错误信息。

## 9. 小结

- LLM 负责生成，Agent 是包含模型、工具、状态和控制循环的完整系统；
- Chain 适合固定步骤，Workflow 适合显式流程，Agent 适合运行时动态决策；
- 模型提出行动，宿主程序验证并执行行动；
- 步骤上限、工具白名单、参数校验和人工审批是 Agent 的基本安全边界；
