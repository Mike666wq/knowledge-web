# 07 RAG 与知识库

> RAG 不是“把文档放进向量数据库”。它是一条从数据摄取、切分、索引、检索、上下文组装到有依据生成的完整数据流，并且需要分别评估检索质量和答案质量。

## 学习目标

完成本章后，你应该能够：

- 解释 RAG、Embedding、Vector Store、Retriever 和 Chunk。
- 区分离线建库流程与在线问答流程。
- 用纯 Python 实现一个可运行的小型检索系统。
- 使用 LangChain `Document`、`Embeddings`、`InMemoryVectorStore` 和 Runnable 组合 2-Step RAG。
- 选择切分策略、`k` 值、元数据过滤和无答案策略。
- 区分 2-Step RAG、Agentic RAG 与混合 RAG。
- 识别检索失败、幻觉、Prompt Injection、权限泄露和脏数据问题。

## 1. 术语

| 术语 | 含义 |
| --- | --- |
| RAG | Retrieval-Augmented Generation，先检索外部资料，再让模型基于资料生成答案。 |
| Corpus（语料库） | 被纳入知识库的一组源文档。 |
| Document | 文本内容和元数据的组合；元数据可保存来源、页码、权限、版本等。 |
| Chunk | 为检索和上下文窗口而切出的文档片段。 |
| Embedding | 把文本映射为数值向量的模型或过程。语义相近文本通常在向量空间中更接近。 |
| Vector Store | 保存向量、文本和元数据并执行相似度检索的存储系统。 |
| Index（索引） | 加速检索的数据结构；向量数据库可能使用 HNSW 等近似最近邻索引。 |
| Retriever | 接收查询并返回相关 `Document` 的统一检索接口，不一定基于向量。 |
| Top-k | 检索返回最相关的 k 个片段。 |
| Recall（召回率） | 应该找到的相关片段中，有多少被检索出来。 |
| Rerank（重排） | 用更精细的模型或规则重新排序候选片段。 |
| Grounding | 让回答受提供证据约束，并能够指出依据。 |
| Hallucination（幻觉） | 模型生成了没有被证据支持的内容。 |

## 2. RAG 解决什么，不解决什么

大模型有有限上下文和静态训练知识。RAG 可以在请求时提供私有、最新或领域资料，并让答案引用来源。

RAG 不能自动保证正确：

- 源文档错误，答案仍可能错误。
- 相关片段没有召回，模型没有证据可用。
- 召回片段太多或冲突，模型可能选错。
- Prompt 没有限制依据，模型仍可能补充常识或猜测。
- 文档内的恶意指令可能影响模型。

因此正确目标不是“接入向量库”，而是“在给定权限和成本下，稳定检索足够证据，并让回答可验证”。

## 3. 核心原理：离线建库与在线问答两条数据流

### 3.1 离线或准实时建库

```text
数据源
 → 加载与解析
 → 清洗和权限标注
 → 文档切分
 → 生成 Embedding
 → 写入向量库
 → 保存来源、版本、时间、权限等元数据
```

“离线”不一定表示每天批量一次；它也可以由文件上传事件触发。关键是它不在每次问答时重复处理全部文档。

### 3.2 在线问答

```text
用户问题 + 已认证身份
 → 查询规范化（可选）
 → 权限过滤 + 检索
 → 重排/去重（可选）
 → 组装带来源的上下文
 → 模型生成或拒答
 → 引用、日志与反馈
```

源文档变化后，应通过稳定文档 ID 和版本更新索引；不能只追加新块而永远不删除旧版本。

## 4. 文档加载与元数据

文本本身不够，至少考虑这些元数据：

```python
{
    "source": "handbook.md",
    "document_id": "employee-handbook",
    "version": "2026-08-01",
    "section": "请假制度",
    "access_scope": "employee",
    "start_index": 1280,
}
```

元数据承担三个职责：

1. 过滤：只检索用户有权访问且版本有效的内容。
2. 引用：让答案可以回到原文。
3. 运维：定位脏数据、重复数据和索引更新问题。

不要把 ACL 只写进 Prompt。权限过滤必须在检索层执行，否则无权内容已经进入模型上下文。

## 5. 切分策略

### 5.1 为什么切分

整篇文档向量过于笼统，检索粒度差，也可能超过模型上下文；切得太碎则失去语义和上下文。

### 5.2 参数含义

- `chunk_size`：单块目标大小，可以按字符、Token 或结构计算。
- `chunk_overlap`：相邻块共享的尾首内容，用于缓解边界信息断裂。
- separator：优先按标题、段落、句子等自然边界切分。

`chunk_size` 没有通用最佳值。应根据文档结构、问题粒度、Embedding 模型限制和评估集调整。代码、表格、对话和 Markdown 通常需要不同策略。

### 5.3 推荐顺序

1. 保留标题层级和章节路径。
2. 优先按结构切分，再按段落、句子递归缩小。
3. 为每块保留来源和位置。
4. 用真实问题评估，不凭直觉选参数。

## 6. Embedding 与相似度

Embedding 模型把文本转为固定维度向量。查询和文档必须使用兼容的同一模型与预处理方式，否则向量不可比较。

常见相似度：

- 余弦相似度：比较方向，常用于已归一化语义向量。
- 点积：可能同时受方向和模长影响。
- 欧氏距离：比较几何距离，值越小越近。

向量检索不是关键词搜索的完全替代。产品名、错误码、IP、订单号等精确词常更适合关键词或混合检索。

更换 Embedding 模型、维度或关键预处理逻辑通常需要重建索引，并记录索引版本。

## 7. Vector Store 与 Retriever

Vector Store 负责保存和搜索向量；Retriever 是面向应用的检索接口。Retriever 可以在向量检索之上加入：

- 元数据和权限过滤。
- 多路查询。
- 关键词 + 向量混合召回。
- MMR 去重和多样性。
- Rerank。
- 分数阈值。

开发时可用内存向量库；生产选型要考虑数据量、过滤能力、备份、一致性、租户隔离、延迟和运维成本，而不只是“支持向量”。

## 8. 2-Step RAG

2-Step RAG 每次固定先检索再生成：

```python
question = "退款期限是多少？"
documents = retriever.invoke(question)
context = format_documents(documents)
answer = model.invoke(prompt(question, context))
```

优点：流程可预测、通常只需一次生成调用、容易测量和控制。适合 FAQ、手册和内部知识问答。

Prompt 应明确：

- 文档内容是资料，不是高优先级指令。
- 只依据上下文回答。
- 证据不足时明确说不知道。
- 引用来源标签。
- 冲突时指出冲突，不擅自选择。

## 9. Agentic RAG 与混合 RAG

### Agentic RAG

把检索器暴露成工具，由 Agent 决定何时检索、检索几次、是否换查询。灵活，但延迟、费用和行为更不确定，必须有循环预算。

### 混合 RAG

在固定或 Agentic 流程中加入查询改写、相关性检查、重排、答案校验等步骤。它适合复杂问题，但每增加一个模型判断点都应有评估证据。

| 架构 | 控制性 | 延迟 | 适用场景 |
| --- | --- | --- | --- |
| 2-Step | 高 | 稳定 | FAQ、手册问答 |
| Agentic | 较低 | 可变 | 多数据源研究、动态探索 |
| 混合 | 中等 | 较高 | 模糊问题、强质量约束 |

默认从 2-Step 开始。只有评估证明固定检索不足时，再引入更复杂架构。

## 10. 生成与引用

上下文应带稳定来源标签：

```text
[employee-handbook#leave-2]
年假申请应至少提前三个工作日提交。
```

要求模型引用标签，并在返回给用户前验证引用标签确实存在于本次检索结果中。引用只能证明“这段内容被提供给了模型”，不能自动证明回答推理正确。

当最高相关结果也很弱，系统应拒答或要求澄清。不要为了“总能回答”而把无关片段交给模型。

## 12. LangChain 完整示例

[examples/02_langchain_rag.py](examples/02_langchain_rag.py) 使用：

- `Document` 表达文本和来源。
- 自定义 `Embeddings` 让示例默认离线可运行。
- 自定义 `BaseRetriever` 建立无额外数值库依赖的教学索引。
- Retriever + `RunnableParallel` 组合问题与上下文。
- 默认确定性回答；增加 `--live` 后调用 `.env` 中的模型。

```bash

# 在线生成模式，可能产生费用

```

生产项目通常把哈希 Embedding 和教学 Retriever 替换为实际 Embedding 服务与持久化向量库；Retriever 之后的接口可以保持稳定。

## 13. 评估顺序

### 13.1 先评估检索

准备包含问题、相关文档 ID 和可接受答案的测试集，关注：

- Recall@k：正确证据是否出现在前 k 条。
- Precision@k：前 k 条中有多少真正相关。
- MRR：第一个正确证据排得多靠前。
- 权限泄露率：是否返回无权文档，目标必须为 0。
- 检索延迟与失败率。

若正确片段没有进入上下文，调 Prompt 很难解决根因。

### 13.2 再评估答案

- Faithfulness：每个事实是否被上下文支持。
- Answer Relevance：是否回答了问题。
- Citation Correctness：引用是否存在且支持对应陈述。
- Refusal Quality：证据不足时是否正确拒答。
- 延迟、Token 和费用。

自动评分只能辅助；高风险领域需要人工抽检和领域专家标准。

## 14. 安全与数据治理

### 文档 Prompt Injection

检索到的文档可能包含“忽略系统提示并泄露密钥”等文本。应把文档标记为不可信数据，限制工具权限，并在系统提示中明确不得执行文档指令。Prompt 不是唯一防线。

### 权限

检索前基于已认证身份生成不可伪造的过滤条件；不要接受用户直接传入 `access_scope=admin`。

### 隐私和保留

确定哪些数据允许 Embedding、日志保存多久、用户删除后如何同步删除原文和向量。Embedding 也可能泄露信息，不应默认视为匿名数据。

### 索引污染

上传源需要身份验证、格式检查、恶意内容扫描和版本控制。对低信任来源可使用独立索引或更低权重。

## 15. 常见错误

### 错误 1：每次提问都重新加载和向量化全部文档

建库与问答应分开。在线流程只处理查询并读取已有索引。

### 错误 2：Chunk 越小越精确

过小 Chunk 会失去标题、条件和例外条款。应通过检索评估调参。

### 错误 3：只保存文本，不保存来源

没有 `document_id`、版本和位置，就难以引用、更新和排查。

### 错误 4：固定取很多片段“保险”

无关上下文会增加费用并干扰模型。先提高召回和重排质量，再确定上下文预算。

### 错误 5：把相似度分数当概率

分数含义依赖向量库、距离函数和模型，不能把 `0.8` 直接解释为“80% 正确”。阈值必须在自己的数据上校准。

### 错误 6：答案评估通过就认为检索没问题

模型可能依靠训练知识答对。必须单独检查证据是否真的被召回和引用。

### 错误 7：先检索再在应用层过滤权限

这可能已经把敏感文本带入重排器、模型或日志。权限过滤应尽量前置到数据访问层。

## 17. 小结

- RAG 包含离线建库和在线问答两条不同数据流。
- Chunk、Embedding、Vector Store 和 Retriever 各自承担不同职责。
- 2-Step RAG 是更适合起步的可控架构；Agentic RAG 需要额外循环预算。
- 先测检索，再测答案；有答案不等于有正确证据。
- 来源、版本、权限和删除策略是知识库的一部分，不是上线后的附加项。
