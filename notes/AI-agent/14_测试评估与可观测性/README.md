# 14 测试、评估与可观测性：证明 Agent 有效

## 学习目标

完成本章后，你应能：

1. 区分确定性测试、离线评估、在线指标和人工评审。
2. 为 RAG、工具调用、最终回答、安全与成本分别定义指标。
3. 构建包含正常、边界、对抗和回归样例的小型评估集。
4. 解释 Recall@k、MRR、参数准确率、忠实度、成功率和分位延迟。
5. 用 trace 串联一次 Agent 的模型、检索、工具和重试过程。
6. 建立“发现失败 → 归因 → 修复 → 回归”的迭代闭环。

## 前置知识

你应已理解 RAG 的文档、分块、检索和生成流程，工具调用的名称与参数契约，以及上一章的结构化日志和请求边界。

## 核心术语

- **Baseline（基线）**：用于比较新版本是否改善的固定系统版本和指标结果。
- **Golden Set（黄金集）**：经过人工确认、包含期望事实或动作的高质量评估样本。
- **Trace/Span**：Trace 表示一次完整请求，Span 表示其中一个可计时、可记录属性的步骤。
- **Regression（回归）**：修改后原本正确的能力发生下降。
- **LLM-as-a-Judge**：使用模型按量表评审输出的方法，必须用人工标签校准偏差。

## 1. 测试、评估和可观测性不是一回事

| 手段 | 回答的问题 | 典型触发时机 |
| --- | --- | --- |
| 单元测试 | 一个确定性函数是否符合契约 | 每次提交 |
| 集成测试 | 模型、向量库、工具能否正确协作 | 合并前或定时 |
| 离线评估 | 固定数据集上的质量是否提升 | Prompt/模型/索引变更时 |
| 在线指标 | 真实流量是否稳定、快速且可负担 | 持续监控 |
| 人工评审 | 机器指标难以表达的有用性与风险如何 | 抽样或高风险场景 |
| 可观测性 | 一次失败具体发生在哪一步 | 调试与事故响应 |

**测试**验证已知契约，通常期望稳定的通过/失败；**评估**度量概率系统质量，结果往往是分数和分布；**可观测性**提供解释这些结果的运行证据。三者缺一不可。

## 2. 先定义任务契约

评估前先写清输入、成功条件和禁止行为。例如知识问答任务：

```text
输入：问题、用户身份、可访问知识库
成功：答案覆盖关键事实，每个事实有可访问来源
禁止：引用越权文档；证据不足时编造；调用写操作工具
预算：P95 < 5 秒，每请求估算成本 < 0.02 元
```

如果“好答案”没有定义，任何评分都会沦为主观体验。

## 3. 测试金字塔

### 3.1 确定性单元测试

最先测试不依赖模型的部分：

- 输入模型和配置校验。
- 文档权限过滤和元数据保留。
- 工具参数校验、白名单和审批条件。
- 状态合并、路由和最大步数。
- Token/成本计算与预算拒绝。
- 错误分类、重试与超时。

### 3.2 录制或模拟的组件测试

通过假的模型客户端固定工具调用或结构化输出，验证控制流。Mock 适合证明“系统如何处理返回”，不适合证明“真实模型会稳定返回”。不要 mock 自己想验证的对象。

### 3.3 真实集成测试

只保留少量高价值样例，连接真实模型和测试环境。设置单独预算、超时和标记，默认单元测试不触发费用。

### 3.4 端到端测试

从 HTTP 输入走到最终答案，验证认证、权限、引用和错误体。端到端测试数量应少，失败后依靠 trace 定位具体组件。

## 4. 构建评估集

评估集不是随便收集十个问题。每条样例至少包含：

```json
{
  "id": "rag-001",
  "category": "fact",
  "question": "超时与重试有什么区别？",
  "expected_facts": ["超时限制一次操作时间", "重试处理短暂失败"],
  "relevant_doc_ids": ["engineering-timeout", "engineering-retry"],
  "expected_tool": null,
  "forbidden": ["无条件重试所有错误"]
}
```

数据集应覆盖：

- 高频正常任务。
- 空输入、歧义、超长输入和依赖失败。
- 不应调用工具的任务。
- 工具名正确但参数容易出错的任务。
- 无答案问题，预期拒答或澄清。
- 提示注入、越权读取和危险写操作。
- 已修复的真实失败案例，作为回归集永久保留。

划分开发集与保留测试集，避免围绕同一批样例反复调 Prompt 造成“评估集过拟合”。

## 5. RAG 指标

RAG 必须把“检索”和“生成”分开评估。

### 5.1 检索指标

- **Recall@k**：前 k 个结果是否覆盖所有相关文档。若相关集合为 `R`，检索集合为 `K`，则 `|R∩K|/|R|`。
- **Hit@k**：前 k 个结果是否至少命中一个相关文档，适合只有一个答案来源的任务。
- **Precision@k**：前 k 个结果中相关结果比例，反映上下文噪声。
- **MRR（Mean Reciprocal Rank）**：第一个相关结果排名倒数的平均值；首位命中得 1，第二位得 0.5。
- **nDCG**：相关性有等级时衡量排序质量。

要保留 `doc_id`、`chunk_id`、来源、分块版本和检索分数，否则无法重现结果。先通过检索指标，再评估生成；否则会把“没取到证据”误判为 Prompt 问题。

### 5.2 生成指标

- **事实覆盖率**：期望关键事实中有多少出现在回答中。
- **忠实度/有据性（Faithfulness/Groundedness）**：回答中的事实是否能由提供的上下文支持。
- **引用准确率**：引用是否真的支持对应陈述。
- **拒答准确率**：证据不足时能否正确拒答，而不是流畅编造。
- **答案相关性**：回答是否针对问题，而不是复述所有上下文。

字符串匹配只适合基线。LLM-as-a-Judge 可以评语义，但评审 Prompt、顺序偏差、模型版本和成本都会影响结果；应抽样人工校准，并保存评审理由。

## 6. 工具调用指标

工具 Agent 至少拆成四层：

| 层 | 指标 | 失败示例 |
| --- | --- | --- |
| 路由 | 工具选择准确率、无需工具准确率 | 查询天气却选择发送邮件 |
| 参数 | Schema 通过率、字段准确率 | 城市正确但日期错误 |
| 执行 | 成功率、超时率、重试次数 | 上游 500 或重复提交 |
| 任务 | 最终任务完成率、人工接管率 | 工具成功但没有完成用户目标 |

不要只看工具执行是否返回 200。调用了错误工具，或者工具结果未被 Agent 正确使用，任务仍然失败。

## 7. 系统与业务指标

建议同时观察四类信号：

- 质量：任务成功率、忠实度、人工满意度、拒答准确率。
- 可靠性：错误率、超时率、重试耗尽率、死循环截断率。
- 性能：首 Token 时间、总延迟、检索/模型/工具各阶段 P50/P95/P99。
- 成本：输入输出 Token、模型费用、检索与工具费用、每成功任务成本。

平均延迟会掩盖长尾，生产看板至少显示 P50 和 P95。成本最好除以成功任务数，因为“便宜但经常失败”不是优化。

## 8. Trace 如何设计

一次请求是一个 trace，每个主要阶段是 span：

```text
trace: answer_request
├── span: authorize
├── span: retrieve
│   └── attrs: top_k, index_version, returned_doc_ids
├── span: model_generate
│   └── attrs: model, input_tokens, output_tokens, finish_reason
├── span: tool_call
│   └── attrs: tool_name, approved, duration_ms, outcome
└── span: response
```

Span 属性应允许聚合但不能泄露敏感内容。记录 Prompt 模板版本与内容哈希，而不是默认记录完整 Prompt；记录文档 ID，而不是完整私密文档。

## 9. 评估流水线

一次模型、Prompt、分块或索引变更都应执行：

1. 固定代码版本、Prompt 版本、模型和数据集版本。
2. 跑确定性测试，失败则停止。
3. 跑检索评估，比较 Recall@k、MRR 和延迟。
4. 跑生成/工具评估，保存每条样例的原始结果和理由。
5. 与基线比较；对关键指标设置回归阈值，而非只看总平均。
6. 人工抽查变化最大和分歧最大的样例。
7. 发布后观察真实流量，确认离线提升没有换来延迟、成本或安全退化。

变更可能有多目标权衡。推荐建立门槛，例如：安全指标不可下降，任务成功率至少持平，P95 延迟最多增加 10%，成本增加需有明确质量收益。

## 10. 失败归因

对失败使用统一标签，避免所有问题都归为“模型不好”：

```text
input / authorization / retrieval / reranking / context_building /
planning / tool_selection / tool_arguments / tool_execution /
generation / citation / policy / timeout / budget / unknown
```

保存最小可重放信息：样例 ID、组件版本、随机参数、模型名、索引版本、工具模拟响应和 trace id。不要为了可重放而存储无必要的个人数据。

## 11. 常见错误

- 只看聊天体验，没有固定评估集和基线。
- 把检索和生成混成一个“回答分数”。
- 使用同一模型生成答案又评判答案，却不做人工校准。
- 平均分提高就发布，忽略安全类别或高价值用户下降。
- 测试真实 API 时没有费用开关和预算上限。
- Trace 记录完整 Prompt、密钥和用户文档。
- 只保留聚合分数，不保留逐样例结果，导致无法归因。

## 12. 完整参考示例

[`examples/evaluation`](examples/evaluation/README.md) 是一个纯标准库离线评估器，包含：

- JSONL 评估集与模拟运行记录。
- RAG 的 Recall@k、Precision@k、MRR。
- 工具选择与参数准确率。
- 事实覆盖率、延迟和成本汇总。
- 安全的 trace/span 记录结构。
- 指标边界测试。

示例故意不调用真实 LLM，让指标定义可重复验证。之后可把真实运行结果转换为相同的 `sample_runs.jsonl` 契约。

## 13. 练习

1. 给数据集增加三条“证据不足应拒答”的样例，并实现拒答准确率。
2. 增加 P95 延迟计算，说明样本量少时其局限。
3. 为工具参数增加字段级准确率，而不是只做整个字典完全匹配。
4. 对两个分块版本运行同一评估集，并写出是否值得发布的结论。
5. 设计一个 LLM Judge 提示词，再用 20 条人工标签估计其一致率。

## 14. 验收清单

- [ ] 每个线上目标至少有一个可自动计算的指标。
- [ ] RAG 检索与生成分别计分。
- [ ] 工具的选择、参数、执行与任务完成分别计分。
- [ ] 数据集包含正常、边界、无答案、对抗和历史回归样例。
- [ ] 每次结果带代码、Prompt、模型、数据集和索引版本。
- [ ] Trace 足够归因，同时默认不保存秘密和私密正文。
- [ ] 发布门槛同时包含质量、可靠性、安全、延迟和成本。

## 小结与下一章

评估把“感觉更聪明”转换为可复现证据，可观测性把总分转换为可修复的组件问题。下一章会把安全策略与成本预算放进执行路径，让系统在面对恶意输入和资源压力时仍保持边界。
